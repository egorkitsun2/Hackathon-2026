# Hackathon-2026 — Backend Specification v0.1

Проект спецификации

10 ноября 2026 · Для согласования

Цель: спроектировать минимальный, но полноценный backend для внутренней системы обратной связи сотрудников «Голос команды».

Спецификация предназначена для двух разработчиков: ты реализуешь серверную часть, Шарапат подключает интерфейс к согласованному API.

Код пока не пишем. Репозиторий `egorkitsun2/Hackathon-2026` и ветки `Backend` / `Frontend` не изменяем.

## 2. Границы MVP

У нас только один основной процесс:

Сотрудник создаёт обращение

Проблема / Предложение / Жалоба / Благодарность

Сервер сохраняет обращение

Статус «Новое», автор, дата

Администратор рассматривает

Изменяет статус и записывает решение

Сотрудник получает результат

Ответ и история изменений

В MVP входят: вход, выход, получение профиля, создание и просмотр обращений, управление статусами, итоговые ответы, история действий.

Не входят: самостоятельная регистрация, СМС, управление аккаунтами через интерфейс, анонимные сообщения, файлы, Telegram, чат, назначение ответственных, редактирование и удаление обращений, расширенная статистика.

Для демонстрации пользователей создаём отдельным seed-скриптом. Реальное создание и восстановление аккаунтов администратором добавим после хакатона.

По ранее согласованному правилу срок рассмотрения — три дня. Пока фиксируем его как бизнес-требование, но автоматический контроль просрочки не включаем в обязательный MVP.

## 3. Ролевая модель

| Операция                   | Employee      | Admin  |
| -------------------------- | ------------- | ------ |
| Вход в систему             |               |        |
| Просмотр своего профиля    |               |        |
| Создание обращения         |               | —      |
| Просмотр своих обращений   |               | —      |
| Просмотр всех обращений    | —             |        |
| Изменение статуса          | —             |        |
| Добавление ответа          | —             |        |

Ключевой принцип: backend самостоятельно определяет пользователя по сессии. Frontend не передаёт роль или идентификатор автора при создании обращения.

## 4. API Contract v1

Все маршруты используют префикс `/api/v1`.

### 4.1. Список endpoints

| Метод   | Путь                 | Успех | Доступ          |
| ------- | -------------------- | ----- | --------------- |
| `GET`   | `/health`            | 200   | Публичный       |
| `POST`  | `/auth/login`        | 200   | Публичный       |
| `POST`  | `/auth/logout`       | 204   | Авторизованный  |
| `GET`   | `/auth/me`           | 200   | Авторизованный  |
| `GET`   | `/tickets`           | 200   | Employee        |
| `POST`  | `/tickets`           | 201   | Employee        |
| `GET`   | `/tickets/:id`       | 200   | Автор или Admin |
| `GET`   | `/admin/tickets`     | 200   | Admin           |
| `PATCH` | `/admin/tickets/:id` | 200   | Admin           |

Итого: 9 endpoints. Этого достаточно для всех обязательных сценариев.

### 4.2. Общие правила JSON

Успешные ответы с телом содержат `data`. Ошибки содержат `error`.

Все даты — ISO 8601, UTC:

`2026-11-10T09:30:00.000Z`

Все идентификаторы — положительные целые числа.

Системные значения:

| Поле     | Допустимые значения                               |
| -------- | ------------------------------------------------- |
| `role`   | `employee`, `admin`                               |
| `type`   | `problem`, `suggestion`, `complaint`, `gratitude` |
| `status` | `new`, `in_review`, `resolved`, `rejected`        |

Для отображения:

| API         | Русский         | Қазақша      |
| ----------- | --------------- | ------------ |
| `new`       | Новое           | Жаңа         |
| `in_review` | На рассмотрении | Қаралуда     |
| `resolved`  | Решено          | Шешілді      |
| `rejected`  | Отклонено       | Қабылданбады |

Frontend самостоятельно преобразует системные значения в выбранный язык.

### 4.3. Авторизация

POST `/api/v1/auth/login`

Запрос:

```

{
  "phone": "+77000000000",
  "password": "example-password"
}

```

Успешный ответ `200`:

```

{
  "data": {
    "user": {
      "id": 1,
      "full_name": "Алия Серикова",
      "phone": "+77000000000",
      "department": "Склад",
      "position": "Кладовщик",
      "role": "employee"
    }
  }
}

```

Сервер одновременно устанавливает сессионную cookie через заголовок `Set-Cookie`. Сам токен сессии в JSON не возвращается.

При ошибке входа сервер отвечает `401` с кодом `INVALID_CREDENTIALS`. Не сообщаем отдельно, существует ли указанный телефон.

GET `/api/v1/auth/me`

Возвращает объект `data.user` того же формата. Используется после перезагрузки страницы для восстановления состояния авторизации.

POST `/api/v1/auth/logout`

Удаляет серверную сессию и очищает cookie.

Ответ: `204 No Content`, без JSON-тела.

### 4.4. Создание обращения

POST `/api/v1/tickets`

```

{
  "type": "problem",
  "title": "Не работает сканер",
  "description": "На складе перестал работать сканер штрихкодов."
}

```

Ответ `201 Created`:

```

{
  "data": {
    "id": 124,
    "type": "problem",
    "title": "Не работает сканер",
    "description": "На складе перестал работать сканер штрихкодов.",
    "status": "new",
    "created_at": "2026-11-10T09:30:00.000Z",
    "updated_at": "2026-11-10T09:30:00.000Z"
  }
}

```

Сервер самостоятельно:

1. Получает `author_id` из сессии.
2. Проверяет и нормализует поля.
3. Создаёт обращение со статусом `new`.
4. Добавляет событие создания в историю.
5. Возвращает созданное обращение.

Операции сохранения обращения и первой записи истории должны выполняться атомарно.

### 4.5. Список обращений сотрудника

GET `/api/v1/tickets?page=1&limit=20`

```

{
  "data": [
    {
      "id": 124,
      "type": "problem",
      "title": "Не работает сканер",
      "status": "new",
      "created_at": "2026-11-10T09:30:00.000Z",
      "updated_at": "2026-11-10T09:30:00.000Z"
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 1
  }
}

```

Правила:

- Показываются только обращения текущего сотрудника.
- Сортировка: сначала новые.
- `page` начинается с 1.
- `limit` по умолчанию 20, максимум 50.
- Если обращений нет, возвращается пустой массив `data: []`.

Для стабильного порядка сортируем по `created_at DESC, id DESC`.

### 4.8. Изменение статуса и ответ

PATCH `/api/v1/admin/tickets/124`

Пример перевода на рассмотрение:

```

{
  "status": "in_review"
}

```

Пример завершения:

```

{
  "status": "resolved",
  "comment": "Оборудование передано на ремонт."
}

```

Ответ `200`:

```

{
  "data": {
    "id": 124,
    "status": "resolved",
    "updated_at": "2026-11-10T11:00:00.000Z",
    "event": {
      "id": 3,
      "old_status": "in_review",
      "new_status": "resolved",
      "comment": "Оборудование передано на ремонт.",
      "created_at": "2026-11-10T11:00:00.000Z"
    }
  }
}

```

При изменении статуса сервер обязательно создаёт запись в `ticket_events`. Текущий статус и история должны оставаться согласованными даже при двух одновременных запросах администраторов.

## 5. Правила изменения статусов

new

Новое

in_review

На рассмотрении

resolved

Решено

rejected

Отклонено

Утверждаем следующие ограничения:

| Правило                       | Поведение сервера            |
| ----------------------------- | ---------------------------- |
| `new → in_review`             | Разрешено                    |
| `in_review → resolved`        | Разрешено, нужен комментарий |
| `in_review → rejected`        | Разрешено, нужен комментарий |
| Изменение на текущий статус   | `409 INVALID_TRANSITION`     |
| Изменение закрытого обращения | `409 INVALID_TRANSITION`     |
| Попытка изменения сотрудником | `403 FORBIDDEN`              |

Для демонстрации достаточно линейного процесса. Переоткрытие, дополнительные статусы и изменение итогового ответа откладываем.

`resolved` означает, что обращение закрыто с положительным решением. Для предложений в комментарии нужно уточнять, что именно принято: согласовано к реализации или уже выполнено. Не стоит смешивать эти факты.

## 6. Валидация данных

| Поле          | Требования                                            |
| ------------- | ----------------------------------------------------- |
| `phone`       | Казахстанский номер, нормализованный в `+7XXXXXXXXXX` |
| `password`    | Непустая строка при входе, без логирования            |
| `type`        | Одно из четырёх допустимых значений                   |
| `title`       | 5–120 символов после `trim()`                         |
| `description` | 10–4000 символов после `trim()`                       |
| `comment`     | 5–2000 символов, обязателен при закрытии              |
| `status`      | Только разрешённые значения и переходы                |
| `id`          | Положительное целое число                             |
| `page`        | Целое число от 1                                      |
| `limit`       | Целое число от 1 до 50                                |

Номер телефона принимаем, например, в форматах `+7 700 000 00 00` и `87000000000`, затем приводим к `+77000000000`.

Это только нормализация логина, не проверка принадлежности телефонного номера сотруднику.

Сервер отклоняет неизвестные поля в изменяющих запросах. Ограничиваем размер JSON-тела, например 8 КиБ. Проверки выполняем на backend независимо от проверок интерфейса.

### Единый формат ошибок

```

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request data",
    "details": {
      "title": "TITLE_TOO_SHORT"
    }
  }
}

```

| HTTP | Код                      | Значение                            |
| ---- | ------------------------ | ----------------------------------- |
| 400  | `VALIDATION_ERROR`       | Некорректные данные                 |
| 401  | `INVALID_CREDENTIALS`    | Неверный телефон или пароль         |
| 401  | `UNAUTHORIZED`           | Нет действующей сессии              |
| 403  | `FORBIDDEN`              | Недостаточно прав                   |
| 403  | `ACCOUNT_DISABLED`       | Учётная запись отключена            |
| 403  | `INVALID_ORIGIN`         | Запрос не прошёл проверку источника |
| 404  | `NOT_FOUND`              | Запись не найдена или недоступна    |
| 409  | `INVALID_TRANSITION`     | Недопустимая смена статуса          |
| 415  | `UNSUPPORTED_MEDIA_TYPE` | Ожидается JSON                      |
| 429  | `RATE_LIMITED`           | Превышен лимит попыток              |

## 7. SQL-схема базы данных

Предлагаю использовать четыре таблицы: `users`, `tickets`, `ticket_events`, `sessions`.

Логическая модель данных

Один пользователь создаёт много обращений и может иметь несколько сессий. У каждого обращения есть последовательность событий обработки; события также связаны с пользователем, который их выполнил.

### SQL Schema v0.1

```

CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    phone TEXT NOT NULL UNIQUE,
    full_name TEXT NOT NULL,
    department TEXT NOT NULL,
    position TEXT NOT NULL,
    password_hash TEXT NOT NULL,
    role TEXT NOT NULL DEFAULT 'employee'
        CHECK (role IN ('employee', 'admin')),
    is_active INTEGER NOT NULL DEFAULT 1
        CHECK (is_active IN (0, 1)),
    created_at TEXT NOT NULL
);

CREATE TABLE tickets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    author_id INTEGER NOT NULL,
    type TEXT NOT NULL CHECK (
        type IN (
            'problem',
            'suggestion',
            'complaint',
            'gratitude'
        )
    ),
    title TEXT NOT NULL
        CHECK (length(title) BETWEEN 5 AND 120),
    description TEXT NOT NULL
        CHECK (length(description) BETWEEN 10 AND 4000),
    status TEXT NOT NULL DEFAULT 'new'
        CHECK (
            status IN (
                'new',
                'in_review',
                'resolved',
                'rejected'
            )
        ),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,

    FOREIGN KEY (author_id)
        REFERENCES users(id)
        ON DELETE RESTRICT
);

CREATE TABLE ticket_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ticket_id INTEGER NOT NULL,
    actor_id INTEGER NOT NULL,
    old_status TEXT CHECK (
        old_status IS NULL OR old_status IN (
            'new', 'in_review', 'resolved', 'rejected'
        )
    ),
    new_status TEXT NOT NULL CHECK (
        new_status IN (
            'new', 'in_review', 'resolved', 'rejected'
        )
    ),
    comment TEXT
        CHECK (
            comment IS NULL OR
            length(comment) BETWEEN 5 AND 2000
        ),
    created_at TEXT NOT NULL,

    FOREIGN KEY (ticket_id)
        REFERENCES tickets(id)
        ON DELETE RESTRICT,

    FOREIGN KEY (actor_id)
        REFERENCES users(id)
        ON DELETE RESTRICT
);

CREATE TABLE sessions (
    token_hash TEXT PRIMARY KEY,
    user_id INTEGER NOT NULL,
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL,

    FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
);

CREATE INDEX idx_tickets_author
    ON tickets(author_id, created_at DESC, id DESC);

CREATE INDEX idx_tickets_status
    ON tickets(status, created_at DESC, id DESC);

CREATE INDEX idx_events_ticket
    ON ticket_events(ticket_id, id);

CREATE INDEX idx_sessions_user
    ON sessions(user_id);

```

Особенности схемы:

- Пароли сохраняются только в `password_hash`.
- Номер телефона должен быть уникальным.
- Пользователей не удаляем при увольнении — устанавливаем `is_active = 0`.
- Время записываем в UTC в стандартизированном ISO-формате.
- История обращений не удаляется вместе с пользователем.
- При выходе удаляется сессия, а не учётная запись.

Ограничения `CHECK` и внешние ключи дополнительно защищают целостность данных. Cloudflare D1 использует SQLite и поддерживает внешние ключи, включённые по умолчанию.&#x20;

Важный момент для реализации: создание обращения и первоначального события, а также изменение статуса и запись истории должны быть атомарными операциями.

D1 поддерживает транзакционное выполнение последовательности SQL-запросов через `batch()`. При конкурентных изменениях также понадобится условное обновление по предыдущему статусу, чтобы два запроса не создали противоречивую историю.&#x20;

## 8. Авторизация и безопасность

Здесь не будем жертвовать безопасностью ради быстрого MVP.

### 8.1. Алгоритм входа

1. Сервер принимает телефон и пароль по HTTPS.
2. Нормализует телефон и проверяет ограничение попыток входа.
3. Находит активного пользователя и проверяет пароль по сохранённому хешу.
4. Генерирует криптографически случайный токен сессии — 32 байта.
5. Сохраняет SHA-256-хеш токена в таблице `sessions`.
6. Отправляет оригинальный токен браузеру в защищённой HttpOnly cookie.
7. При следующих запросах проверяет сессию, срок действия и активность пользователя.

SHA-256 здесь используется только для случайного токена сессии. Для паролей обычный SHA-256 не подходит — нужен специализированный медленный алгоритм.

### 8.2. Хеширование паролей

Предпочтительный алгоритм — Argon2id. В Workers Web Crypto поддерживается PBKDF2, но нужно проверить производительность безопасной конфигурации.

Ориентир OWASP для PBKDF2-HMAC-SHA-256 — не менее 600 000 итераций.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://cheatsheetseries.owasp.org\&sz=32)

OWASP Cheat Sheet Series+1



Поэтому фиксируем правило: не снижать количество итераций ради того, чтобы приложение укладывалось в бесплатный лимит Workers.

Первый технический тест после утверждения спецификации — реальное измерение стоимости хеширования и проверки пароля. Если Workers Free не подходит, переносим backend в обычный Node.js runtime, сохраняя API-контракт.

### 8.3. Cookie

Для production:

```

Set-Cookie: __Host-session=<opaque-token>;
  Path=/; HttpOnly; Secure; SameSite=Lax;
  Max-Age=28800

```

Здесь `opaque-token` — условное обозначение случайного токена, а не его реальное значение.

- `HttpOnly` — JavaScript не может прочитать cookie.
- `Secure` — передаётся только по HTTPS.
- `SameSite=Lax` — ограничивает межсайтовую отправку cookie.
- `Max-Age=28800` — срок сессии 8 часов.
- `__Host-` — cookie привязана к текущему хосту, без атрибута `Domain`.

Для локальной разработки на HTTP потребуется отдельная конфигурация cookie. В production `Secure` обязателен.

Не используем `localStorage` для хранения сессионных токенов.

### 8.4. CSRF, CORS и права доступа

Поскольку frontend и backend используют один origin:

- Не включаем разрешающий CORS для сторонних сайтов.
- На всех изменяющих запросах проверяем `Origin` на точное совпадение с разрешённым адресом.
- Отклоняем отсутствующий или чужой `Origin` для защищённых cookie-based запросов.
- Используем JSON-запросы с проверкой `Content-Type`.
- На сервере проверяем роль пользователя и принадлежность каждого обращения.
- Приватные API-ответы помечаем `Cache-Control: no-store`.

Одного `SameSite=Lax` недостаточно для полноценной защиты от CSRF. Поэтому проверка источника является обязательной частью спецификации.&#x20;

## 9. Контракт для Шарапата

Вот что фронтенд должен знать уже сейчас.

| Действие в интерфейсе  | Запрос                     | Что делать с ответом               |
| ---------------------- | -------------------------- | ---------------------------------- |
| Открыть приложение     | `GET /auth/me`             | Определить роль и показать кабинет |
| Войти                  | `POST /auth/login`         | Открыть кабинет                    |
| Выйти                  | `POST /auth/logout`        | Вернуться к авторизации            |
| Открыть мои обращения  | `GET /tickets`             | Показать список                    |
| Отправить обращение    | `POST /tickets`            | Показать результат и номер         |
| Открыть обращение      | `GET /tickets/:id`         | Показать детали и историю          |
| Открыть админ-панель   | `GET /admin/tickets`       | Показать общую очередь             |
| Завершить рассмотрение | `PATCH /admin/tickets/:id` | Обновить статус и историю          |

Все пути в таблице относительно `/api/v1`.

Пример вызова API с фронтенда:

```

const response = await fetch("/api/v1/tickets", {
  method: "POST",
  credentials: "same-origin",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify({
    type: "problem",
    title: "Не работает сканер",
    description: "На складе сломался сканер."
  })
});

const result = await response.json();

if (!response.ok) {
  throw new Error(result.error?.code ?? "UNKNOWN_ERROR");
}

console.log(result.data);

```

Это пример использования контракта, а не уже работающий запрос.

Frontend не должен самостоятельно генерировать ID обращений, назначать серверные статусы или определять права пользователя по сохранённому локально значению роли.

Для двух языков ему достаточно словарей переводов. Backend возвращает одинаковые системные коды независимо от языка.
