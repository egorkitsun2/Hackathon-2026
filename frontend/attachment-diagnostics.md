# Проверка вложений, 11 ноября 2026

## Подтверждённые факты

- В основной локальной SQLite выполнены только SELECT в режиме readOnly.
  У обращений 7, 8, 9 статус new и 0 записей ticket_attachments.
  Это отсутствие сохранённого вложения, а не доказательство ошибки отображения.
- localhost:8787 отвечает 200 на /api/v1/health и отдаёт актуальные api.js/ticket.js
  с загрузкой и отрисовкой вложений. Это не проверяет кэш уже открытой вкладки.
- POST /api/v1/tickets/9/attachments без сессии возвращает 401 UNAUTHORIZED.
  На основной базе авторизованные изменяющие запросы не выполнялись.
- Изолированная проверка через реальный HTTP-сервер, frontend/js/api.js,
  SQLite :memory: и отдельное временное хранилище: корректный PDF с именем
  фото.pdf загружается; в деталях сотрудника и администратора есть одна запись,
  защищённое скачивание возвращает 200 и исходное содержимое.
- Файл пользователя не предоставлен; содержимое и MIME именно его файла
  не проверены. Выбор файла в форме не доказывает успешный POST.

## Выполненные проверки

Из корня: `node --test frontend/tests/*.test.mjs`.

Из backend:

```powershell
$env:TEST_HTTP = '1'
node --import tsx ../frontend/tests/create-ticket.integration.mjs
node --import tsx --test tests/attachments.test.ts
```

HTTP-проверка прошла после отключения повторного использования соединений
в тестовом клиенте (Connection: close). При первом прогоне с пулом Node fetch
успешная загрузка/чтение обеими ролями прошли, но отрицательная загрузка в
закрытое обращение дала NETWORK_ERROR вместо ожидаемого ATTACHMENTS_LOCKED.
Контракт предусматривает закрытие upload-соединения после ответа. Связь этой
особенности Node-клиента с отказом в Firefox не установлена. Повторного POST
автоматически нет; Connection: close в браузерный код не добавлялся.

7 тестов backend прошли: четыре формата, метаданные/скачивание/права,
неверные multipart/имена/типы/размеры, квота при конкуренции, изменение
статуса/сессии во время загрузки, ровно 5 МиБ, откат INSERT и неопределённый
результат COMMIT. Два сообщения Unexpected API error относятся к намеренно
внедрённым сбоям БД в последних тестах; сами тесты прошли.

## Изменение frontend

После частичного сбоя создания показывается конкретная переведённая причина:
тип/содержимое файла, размер, имя, статус, квота, отсутствие маршрута, сеть,
тайм-аут и другие коды. Ранее оставалось только общее предупреждение.
Номер уже созданного обращения сохраняется; автоматической переотправки нет.

## Чего не хватает для вывода о конкретном отказе

Текст результата отправки (0/1 или 1/1 и причина), HTTP-статус/код ответа
POST /api/v1/tickets/:id/attachments либо сам исходный файл для воспроизведения.
Не передавать cookies, пароли и токены. Дефект backend, объясняющий именно
отсутствие файла пользователя, пока не подтверждён.

Дополнение: после установки Playwright полный сценарий проверен в настоящем
Firefox на 1280 и 390 px, с загрузкой, отображением и скачиванием обеими ролями.
Оба прогона прошли. Подробности и скриншоты: [qa/report.md](qa/report.md).
