# Запуск с backend Егора

## Руководители и маршрутизация (API v0.5)

В новом обращении сотрудник обязательно выбирает активное направление из
`GET /api/v1/categories?details=true`. Коды и названия (`name_ru`, `name_kz`)
приходят с backend; фиксированного списка во frontend нет. Конкретного
руководителя сотрудник не выбирает и его ID при создании обращения не передаёт.

В «Маршрутизации» администратор создаёт направления с неизменяемым кодом
(`a-z`, затем `a-z0-9_`, 2–32 символа), двумя названиями (1–120 символов после trim)
и необязательным активным руководителем. Используются согласованные
`GET/POST /api/v1/admin/categories` и `PATCH /api/v1/admin/categories/:code`.
«Удалить» после подтверждения отправляет `{is_active:false}`: данные и назначения
сохраняются. Переключатель архива позволяет восстановить направление через
`{is_active:true}`. Направление по умолчанию `general` нельзя архивировать.
Изменение ответственного остаётся в существующем `/admin/routing/:code`.

В ответах обращений ожидается согласованный объект
`category: {id, name_ru, name_kk}` — он сохраняет локализованное название архивного
направления для сотрудника, руководителя и администратора. Обратите внимание:
казахское имя в ответе обращения — `name_kk`, в справочнике — `name_kz`.
Старые строковые значения отображаются через загруженный справочник, при
отсутствии записи показывается код без выдуманного названия.

Новый API направлений на момент реализации отсутствовал в локальном backend
(`a1d53aa`). Браузерная проверка `frontend/qa/categories-browser.mjs` использует
явные локальные тестовые ответы по согласованному контракту, авторизацию на
отдельной базе `:memory:` и не подменяет API в самом приложении. Перед сдачей
нужна повторная проверка с новой версией backend Sol.

Роль `manager` входит через ту же страницу входа. Временный пароль необходимо
сменить, после чего открывается `#/manager`: только текущие назначения, фильтр
статуса, общие с администратором детали, история и защищённые вложения. Руководитель
может взять обращение на рассмотрение и завершить/отклонить с комментарием.
Создание обращений, загрузка файлов, управление пользователями и статистика
руководителю недоступны. При 404/403 после переназначения карточка очищается,
открывается обновлённая очередь. Уже полученные пользователем данные отозвать нельзя.

Администратор в «Пользователях» создаёт сотрудников и руководителей, переключает
их списки, блокирует/активирует и сбрасывает пароли с однократным показом.
Правила направлений находятся в отдельной вкладке «Маршрутизация» (`#/admin/routing`),
пользователи — в `#/admin/users`. Переключение работает без перезагрузки страницы.
В очередь добавлены текущий
ответственный и фильтр «Только без ответственного»; в деталях — ручное назначение.
Фильтр «Требуют переназначения» отправляет `needs_reassignment=true` и сочетается
со статусом и «Только без ответственного» по AND. Очередь показывает текстовую
отметку для `needs_reassignment: true`, полученного от backend. Это незавершённые
обращения без исполнителя или с заблокированным руководителем; закрытые обращения
не включаются. Сам frontend этот признак не вычисляет. После назначения активного
руководителя или повторной активации прежнего отметка исчезает при обновлении очереди.
Варианты назначения берутся из всех страниц списка руководителей. Предлагаются
активные manager; заблокированное текущее назначение помечается отдельно.
«Ответственный не назначен» отправляет явный null. Правило влияет только на новые
обращения, ручное назначение — только на выбранное обращение.

В карточке направления есть отдельная кнопка «Снять назначение»: она отправляет
существующий PATCH с `manager_id: null`. Новые обращения по этому направлению
попадают в общую очередь администратора; ранее назначенные обращения не меняются.
Перед блокировкой руководителя frontend проверяет правила и страницы очереди
через существующие GET API. При наличии назначений показывается подтверждение
с предупреждением, что незавершённые обращения могут потребовать переназначения,
и указанием нового фильтра. Если проверить назначения
не удалось, предупреждение прямо сообщает об этом. Автоматического переназначения
или изменения серверной логики блокировки frontend не выполняет; проверка —
снимок состояния. Блокировка/активация сохраняет назначения, даты и историю;
backend вычисляет актуальный флаг при чтении очереди.
Заблокированный руководитель остаётся явно помеченным в списке и правилах.

Все действия используют настоящий same-origin API v0.5 с cookie. При потере
ответа на изменение перечитываются данные без автоматического повтора PATCH;
сообщение остаётся предупреждением. 409 обновляет карточку, не выдавая успех.

**Ограничение backend:** в очереди и деталях manager API не возвращает объект
автора. В очереди показано «Автор недоступен для вашей роли»; имя автора не
восстанавливается из истории. Администратор видит штатный объект author.
Если руководителю необходимо именно имя автора в очереди, Sol должен отдельно
согласовать и добавить это поле. История API содержит изменения статуса,
но не события смены назначений или правил — frontend их не выдумывает.

Проверки: `node --test frontend/tests/*.test.mjs` из корня. Браузерная проверка
реального backend выполняется из `backend/`:

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = (Resolve-Path ../frontend/.cache/ms-playwright).Path
node --import tsx ../frontend/qa/manager-routing-browser.mjs
node --import tsx ../frontend/qa/admin-tabs-browser.mjs
node --import tsx ../frontend/qa/reassignment-filter-browser.mjs
```

Нужны уже установленные локальные Playwright/Firefox. Сценарий создаёт базу
в памяти и временные файлы, использует искусственные аккаунты и не обращается
к основной базе. Журнал и скриншоты — `frontend/qa/runtime/manager-routing/`
(исключены из Git). Он проверяет обе очереди, временные пароли, PNG/PDF,
решение, переназначение, блокировку/активацию, сброс пароля, настоящие 409/404,
потерю ответа после сохранённого PATCH, RU/KZ, обе темы и пять ширин экрана.

## Остальной интерфейс

Modern SaaS-редизайн: общая навигация по роли, карточки с бейджами статусов,
основное действие рядом с заголовком, отдельная панель рассмотрения и мобильные
карточки вместо таблицы. В «Сотрудниках» раскройте «Создать сотрудника»;
одноразовый пароль появляется в модальном результате и очищается при закрытии.
Светлая/тёмная палитры и размеры задаются CSS-переменными в styles.css.
UX-аудит и проверка пяти разрешений: qa/redesign-audit.md.

В форме нового обращения под темой есть короткая рекомендация, а под описанием —
свёрнутый блок «Как правильно описать обращение?». Вопросы меняются для проблемы,
предложения, жалобы и благодарности, переводятся на РУС / ҚАЗ. Подсказки не
заполняют поля и не входят в запросы; смена типа/языка сохраняет текст и файлы.

Кнопка солнца/луны в общей шапке переключает светлую и тёмную тему на всех
экранах. Выбор сохраняется в localStorage под ключом `team-voice-theme`.
Если выбора нет, используется системный prefers-color-scheme; изменения
системной темы учитываются до первого явного выбора. Начальная тема задаётся
скриптом theme-init.js до подключения CSS. Формы, вложения и авторизация при
переключении не сбрасываются. Основные цвета обеих тем — CSS-переменные в
styles.css; если localStorage запрещён браузером, переключение остаётся
доступным в текущей вкладке без гарантии сохранения после reload.

В форме нового обращения выбранные вложения видны до отправки: изображения
JPG/JPEG, PNG и WebP — миниатюрами, PDF — карточкой с обозначением PDF.
У каждого файла показаны имя, размер и кнопка удаления. Повторный выбор
добавляет файлы, всего до трёх; превышение лимита не удаляет уже выбранные.
Можно убрать один файл или очистить все. До отправки запросов загрузки нет;
после отправки загружаются только оставшиеся файлы по прежнему API.
Временные object URL освобождаются при удалении, очистке, уходе из формы
и отправке. При возврате в незавершённую форму миниатюры создаются заново;
файлы хранятся только в оперативной памяти текущей сессии.

После исправлений аудита: список сотрудника сохраняет страницу при возврате
из деталей; старые запросы не завершают новый вход. В окне сброса пароля можно
отменить ожидание, максимальное ожидание — 30 секунд; при неизвестном результате
повторный сброс требует подтверждения. Лимит входов на номер считает неверные
пароли, а оставшееся время приходит в Retry-After и отображается обратным отсчётом.
Общий защитный лимит по IP сохранён. Для новой политики перезапустите backend;
старые счётчики в базе не очищаются автоматически при обновлении.

Сброс пароля: администратор → «Сотрудники» → «Сбросить пароль» → проверить
имя и телефон → «Подтвердить сброс». Отправляется один POST с `{}`; строка
обновляется из ответа сервера. Временный пароль показывается один раз,
копируется только по кнопке; при отказе буфера его можно выделить вручную.
При закрытии окна, переходе или выходе пароль удаляется из DOM и памяти
состояния интерфейса. Пароль не сохраняется в браузерных хранилищах или отчётах.

Сброс отзывает старые сессии и требует смены временного пароля при входе.
Заблокированный аккаунт нужно активировать отдельно. При потере ответа
автоматического повтора нет; новый сброс требует нового подтверждения.
Конфликт `PASSWORD_CHANGED` при сбросе обновляет список сотрудников и не
завершает сессию администратора.

Браузерная проверка сброса (при установленном тестовом Firefox/Playwright)
из backend: `node --import tsx ../frontend/qa/password-reset-browser.mjs`,
с `PLAYWRIGHT_BROWSERS_PATH`, указывающим на `frontend/.cache/ms-playwright`.
Тест использует базу в памяти и искусственные аккаунты; снимки результата
с временным паролем не сохраняются.

Открывайте сайт через backend на **http://localhost:8787**. Live Server и
`python -m http.server` не обслуживают API и не подходят для проверки входа.

В терминале PowerShell из корня репозитория:

```powershell
$env:FRONTEND_DIR = (Resolve-Path ./frontend).Path
$env:APP_ORIGIN = 'http://localhost:8787'
cd backend
npm.cmd ci
# Только для первой подготовки пустой базы:
npm.cmd run seed
npm.cmd run dev
```

Seed создаёт два аккаунта сотрудника и один администратора. Телефоны и случайные
пароли находятся в `backend/.local/test-accounts.json`. Откройте этот файл локально
и используйте аккаунт с `role: "employee"`. Не публикуйте файл с паролями.
При уже созданных аккаунтах повторно запускать seed не нужно.

Настоящие вход, проверка сессии после перезагрузки, выход и список своих обращений
и создание обращений подключены. Роль берётся из ответа backend.

Для просмотра очереди войдите аккаунтом с `role: "admin"` из того же локального
файла тестовых аккаунтов. Администратору доступны список всех обращений, фильтр
по статусу, пагинация и подробный просмотр с данными автора. Фильтр и страница
сохраняются при возврате из деталей и сбрасываются при выходе. На компьютере
показывается таблица, на телефоне — карточки.

В деталях нового обращения нажмите «Взять на рассмотрение». Затем выберите
«Решить» или «Отклонить», введите обязательный комментарий 5–2000 символов и
нажмите «Сохранить решение». После ответа API статус, ответ и история
перезагружаются с сервера. Закрытые обращения доступны только для просмотра.
При конфликте статусов загружается актуальное состояние; при потере ответа
запрос изменения не повторяется автоматически. Комментарий сохраняется при
смене языка и очищается после успешного сохранения либо выхода из деталей.

В панели администратора ссылка «Сотрудники» открывает `#/admin/users`: список,
создание, блокировка и активация аккаунтов. ФИО, отдел и должность — 1–120
символов. Роль сотрудника и временный пароль назначает сервер. После создания
передайте показанные телефон и пароль лично сотруднику. Результат отображается
однократно и очищается при закрытии, переходе или выходе; пароли не сохраняются
в хранилище браузера. При потере ответа создания список обновляется, но повторить
получение временного пароля или сбросить пароль через сайт пока нельзя.

Для нового сотрудника вход и восстановление сессии читают заголовок
`X-Password-Change-Required`. До смены пароля любые ссылки ведут на
`#/change-password`, запросы обращений не отправляются. Требуются текущий пароль,
новый (12–128 Unicode-символов, до 1024 UTF-8 байт) и его повтор. Пароли не
обрезаются. После успеха открывается кабинет; cookie обновляет сервер.
Блокировка отзывает сессии сотрудника; после активации нужно войти заново.
Существующие тестовые аккаунты могут не требовать смены пароля — проверяйте
этот сценарий на новом сотруднике. Все новые экраны доступны на РУС / ҚАЗ.

После входа сотрудником нажмите «Создать обращение», выберите тип и заполните
тему и описание. После отправки сервер вернёт номер обращения; ссылка
«Перейти к моим обращениям» открывает обновлённый список. При сетевом сбое
проверьте список перед повторной отправкой: ответ мог потеряться после сохранения.

«Подробнее» в списке или после отправки открывает описание, статус, ответ
администрации и историю. Прямая ссылка имеет вид `#/tickets/1` и работает после
перезагрузки с действующей сессией. Чужое или отсутствующее обращение показывает
сообщение о недоступности. Назад можно вернуться ссылкой или кнопкой браузера.

Проверки frontend из корня репозитория:

```powershell
node --test frontend/tests/*.test.mjs
```

Интеграционная проверка с настоящим backend использует SQLite в памяти,
не изменяя локальную базу и аккаунты. При установленных зависимостях backend:

```powershell
cd backend
node --import tsx ../frontend/tests/create-ticket.integration.mjs
```

Интеграционный сценарий также проверяет создание сотрудника, обязательную смену
пароля, отзыв старых сессий, создание обращения, блокировку и повторный вход
после активации. Это проверка API с реальным backend; визуальный браузерный тест
