# Проверка проекта — 12 ноября 2026

Проверена ветка `Frontend`, исходный commit `4627a92`. Найдены **три воспроизводимых дефекта frontend**. Исчезновение предпросмотра именно по общей ссылке остаётся нерешённым: на локальных HTTP и HTTPS с текущими исходниками обычная загрузка проходит. Оснований объявлять причиной backend нет.

Изменены только материалы проверки в `frontend/qa/`. Исправления функционального кода в этом этапе не вносились, коммита и отправки изменений нет.

## Подтверждённые дефекты

### 1. Предпросмотр не выходит из состояния загрузки при зависшем запросе

**Приоритет: средний.**

Шаги: открыть обращение с PNG; задержать бинарный GET вложения без ответа; продвинуть браузерные часы на 120 секунд. Имя и «Скачать» остаются, под ними — «Загрузка предпросмотра…». Кнопки повтора нет. После получения ответа изображение появляется.

Причина: `frontend/js/ticket.js:42` создаёт AbortController, но не ограничивает время ожидания. Ручной повтор доступен только после ошибки, а зависший запрос её ещё не вернул.

Это **не доказанное объяснение пользовательского случая**: пользователь видит только «Скачать», без надписи о загрузке.

Доказательства: [снимок](runtime/full-audit/deep-stalled-preview.png), [журнал](runtime/full-audit/deep-audit-results.json), finding `PREVIEW-TIMEOUT`.

### 2. Администратор попадает в пустой список после обработки последней записи страницы

**Приоритет: средний.**

Шаги: создать 21 новое обращение; у администратора выбрать фильтр «Новые»; открыть единственную запись со второй страницы; взять её на рассмотрение; вернуться к списку.

Фактически: отображается пустой результат, пагинация исчезает, хотя в базе ещё 20 новых обращений. Переключение фильтра восстанавливает список.

Причина: `frontend/js/admin.js:107` сохраняет прежний номер страницы при уменьшении количества результатов. В отличие от списка сотрудника, отсутствует переход на последнюю существующую страницу. Пагинация скрывается при total <= limit (`admin.js:77`).

Доказательства: [снимок](runtime/full-audit/deep-admin-empty-last-page.png), finding `ADMIN-PAGE-CLAMP` в журнале.

### 3. Отклонённый четвёртый файл мешает отправить три допустимых

**Приоритет: низкий, неудобство формы.**

Шаги: заполнить форму; выбрать три допустимых файла; повторным выбором попробовать добавить четвёртый. Четвёртый отклоняется, три первых остаются. Нажать «Отправить».

Фактически: запрос создания не отправляется из-за сохранённой ошибки выбора, хотя оставшиеся три файла допустимы. Чтобы продолжить, приходится удалить файл или очистить выбор.

Причина: `frontend/js/new-ticket.js:210` сохраняет прежний `filesError` через `filesError || ...`, вместо проверки фактически оставшегося набора.

Доказательства: [снимок](runtime/full-audit/deep-valid-files-blocked.png), finding `REJECTED-FILE-BLOCKS-VALID-SELECTION` в журнале.

## Исчезновение PNG по общей ссылке

Проверены реальные цветные изображения 640×360, а не только прежний почти белый PNG 1×1. Подтверждены декодирование, ненулевые размеры элемента и видимость; сохранены снимки. Предыдущий тест с PNG 1×1 был недостаточен для содержательной визуальной проверки.

| Набор | Сотрудник | Администратор | Повторное открытие/reload | HTTP / локальный HTTPS |
|---|---|---|---|---|
| Только PNG | Прошёл | Прошёл | Прошёл | Прошёл |
| PNG + PDF | Прошёл | Прошёл | Прошёл | Прошёл |
| PNG + JPEG + WebP | Прошёл | Прошёл | Прошёл | Прошёл |

В текущем `ticket.js` PNG с `mime_type: "image/png"` и положительным числовым `id` обязательно получает контейнер предпросмотра: загрузка → изображение либо ошибка с повтором. Только «Скачать», без картинки и сообщений, требует проверки **версии выданного JavaScript и метаданных конкретного вложения**. Устаревший frontend либо несовпадающие метаданные — гипотезы, а не установленная причина. Одновременный выбор PDF воспроизвести проблему не помог.

Общая ссылка не открывалась, реальные аккаунты не использовались. Локальный HTTPS проверяет production-режим и Secure cookie, но не кэш, прокси и фактический frontend общей ссылки. На `localhost:8787` во время проверки сервер не отвечал; сравнить его выдачу с рабочей папкой не удалось.

Для диагностики на проблемной странице можно вручную выполнить в консоли браузера следующий **только читающий** код. Он не выводит cookie, пароли, имена файлов и содержимое обращений:

```js
console.log('app', document.querySelector('script[type="module"]')?.getAttribute('src'));
console.log('preview elements', document.querySelectorAll('#attachments-list .attachment-image-preview').length);
const id = location.hash.match(/\/tickets\/(\d+)$/)?.[1];
if (id) {
  const response = await fetch(`/api/v1/tickets/${id}`, {
    credentials: 'same-origin', cache: 'no-store'
  });
  console.log('details status', response.status);
  if (response.ok) {
    const result = await response.json();
    console.table((result.data.attachments ?? []).map(file => ({
      id: file.id, id_type: typeof file.id, mime_type: file.mime_type
    })));
  }
}
```

Ожидаемый app: `js/app.js?v=saved-previews-20261112-1`; PNG должен иметь `mime_type: image/png`, `id_type: number`. Эти данные помогут отличить проблему выдаваемой версии от обработки метаданных, не меняя основную базу.

Снимки работающего варианта: [сотрудник, PNG](runtime/full-audit/deep-png-only-employee.png), [администратор, PNG + PDF, телефон](runtime/full-audit/deep-png-pdf-admin-mobile.png).

## Воспроизводимость и ограничения

Все данные искусственные. Использованы базы `:memory:` и отдельная SQLite в проверяемом временном каталоге. Каталоги вложений и локальный сертификат удалены после тестирования. Основная база, реальные пароли и backend-файлы не менялись.

Основные журналы и снимки находятся в `frontend/qa/runtime/full-audit/` (папка исключена из Git). HTTPS-журнал — `https/deep-audit-results.json`; HTTP — `deep-audit-results.json`; сохранность базы и статические проверки — `supplementary-results.json`.

Из `backend/` при установленных локальных Playwright/Firefox:

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = (Resolve-Path ../frontend/.cache/ms-playwright).Path
node --import tsx ../frontend/qa/deep-audit-browser.mjs
$env:QA_HTTPS = '1'
node --import tsx ../frontend/qa/deep-audit-browser.mjs
Remove-Item Env:QA_HTTPS
node --import tsx ../frontend/qa/persistence-audit.mjs
```

HTTPS-проверка использует установленный Git OpenSSL для временного сертификата; недоверие к нему игнорируется только в тестовом контексте браузера.

Найденные дефекты записываются в findings; успешное завершение сценария означает завершённую проверку, **не отсутствие дефектов**. Исправлять их следует отдельным этапом с повторным запуском этих воспроизведений.

Не проверены: фактическая общая ссылка и её кэш/прокси, проблемный пользовательский PNG, физические телефоны, другие браузерные движки, нагрузка и все возможные сочетания состояний. Полного отсутствия ошибок эти проверки не гарантируют.
