# Аудит MVP v0.3, этап 1

Дата: 2026-11-10. Исходное состояние: Backend, 3413ddb, чистое рабочее дерево.
Архитектура Node.js + Hono + SQLite и API сохранены; frontend/main не менялись.

## Подтверждённые проблемы и исправления

1. **Windows npm ci / EPERM.** В журнале npm и списке загруженных модулей
   подтверждено: ранее запущенный backend PID 12620 удерживал
   node_modules/argon2/prebuilds/win32-x64/argon2.glibc.node. После прерванного ci
   отсутствовали TypeScript и tsx. Сохранён SQLite backup, остановлен только
   проверенный сервер, npm ci успешно восстановил 20 пакетов. Другие процессы
   и пользовательские данные не удалялись. Работающий сервер снова запущен на
   localhost:8787 с прежней базой и frontend; страница и health вернули 200.
2. **Bootstrap оставлял файл при сбое COMMIT.** Ошибка воспроизведена через
   deferred foreign key: аккаунт откатывался, файл с паролем оставался. После
   исправления при обычных ошибках записи/COMMIT удаляется только созданный
   этой попыткой файл (проверяются dev/ino). Существующий или заменённый файл
   не удаляется. Файл создаётся эксклюзивно и синхронизируется до COMMIT.
   Регрессионный тест до исправления падал, после проходит.
3. **Удобство CLI.** Без обязательных длинных аргументов теперь поочерёдно
   запрашиваются недостающие поля; поддержаны вставка нескольких строк, неверный
   ввод, EOF/Ctrl+C, --help. Старые аргументы работают. Пароль не запрашивается
   и не печатается; остаётся приватным локальным файлом, исключённым из Git.

## Что проверено в коде и сценариях

Argon2id (64 MiB, t=3, p=1), случайные токены сессий и хранение только их
SHA-256-хешей; HttpOnly/SameSite и Secure в production; роли, владелец обращения,
точный Origin; лимиты входа и конкурентной работы Argon2. Утечек паролей/хешей
через user/ticket GET-ответы в проверенном коде не обнаружено.

Bootstrap допускает только первого admin, включая отказ при заблокированном
admin; повтор и конкуренция не создают дополнительных администраторов. Старые
пользователи, обращения, история и сессии сохраняются при миграциях.

Новый employee получает временный пароль один раз; до смены доступ ограничен
me/logout/change-password. Смена пароля и замена сессии атомарны. Блокировка
отзывает все сессии, активация не восстанавливает старые. Запись обращения
повторно проверяет сессию после чтения тела запроса. Временные тестовые данные
изолированы от существующей базы.

## Ограничения интеграции

Текущий frontend ещё не читает X-Password-Change-Required и не содержит новых
форм. Нельзя объявлять новый employee-процесс готовым через UI до их добавления.
[ТЗ для Шарапата](frontend-v03-handoff.md) содержит точные маршруты, поля,
ответы и обработку ошибок. [Windows-инструкция](windows-local-setup.md)
описывает зависимости, интерактивный bootstrap и запуск сайта.

Повторный POST создания при потере ответа вернёт PHONE_EXISTS; восстановление
утраченного временного пароля не входит в этап. Автоматических повторов POST
во frontend быть не должно. За общим reverse proxy IP-квота входов общая.
SQLite и файловая система не дают общей crash-atomic транзакции; после аварийного
завершения bootstrap оператор проверяет оставшийся credential-файл и БД локально.
На Windows POSIX mode не заменяет приватные ACL.

Подтверждённых иных ошибок авторизации/API по проведённым проверкам нет.
База не удалялась; backup и контрольные суммы сохранены в Git-игнорируемом .local.
Merge, push и публичное развёртывание не выполнялись.
