# Шарапат: интеграция frontend с backend v0.3, этап 1

Цель: добавить обязательную смену пароля и управление сотрудниками, сохранив
существующие экраны обращений. Все запросы идут на текущий origin, `/api/v1`,
с `credentials: 'same-origin'`; POST/PATCH используют JSON. Регистрации
администратора в браузере нет. Полный источник: [api-contract.md](api-contract.md).

## 1. Определение обязательной смены пароля

`POST /auth/login` и `GET /auth/me` сохраняют прежний JSON `{data:{user}}`.
Признак находится **в HTTP-заголовке** `X-Password-Change-Required`: `true` или
`false`. Текущий `frontend/js/api.js` отбрасывает заголовки: сохранить этот признак
как отдельные метаданные результата в API-обёртке, затем использовать в
`app.js` и при входе, и при восстановлении сессии. JSON backend не менять.

Если признак true, до любых запросов списка/деталей обращений показывать экран
смены пароля. Прямые ссылки и перезагрузка также должны вести на этот экран.
На любой ответ `403 PASSWORD_CHANGE_REQUIRED` переключаться туда же. Это
дополняет серверный запрет: до смены доступны только me, logout, change-password.

Экран: текущий/временный пароль, новый пароль, повтор нового пароля, кнопки
«Сменить пароль» и «Выйти». Новый пароль: 12–128 Unicode-символов, максимум
1024 UTF-8 байта, не только пробелы, без NUL, отличается от текущего. Не обрезать
и не нормализовать пароли. Повтор проверяется только в UI, на сервер не уходит.

`POST /auth/change-password`:

```json
{"current_password":"<временный или текущий>","new_password":"<новый>"}
```

Ответ 200: `{data:{user:{id,full_name,phone,department,position,role}}}`;
заголовок `X-Password-Change-Required: false`. Сервер сам обновляет HttpOnly
cookie, отзывает все старые сессии. Очистить поля и открыть кабинет по роли.
Токен сессии в JS не читать и не хранить. Для неверного текущего пароля
`401 INVALID_CREDENTIALS` — показать ошибку формы, не считать это истечением
сессии. При `401 UNAUTHORIZED` — вернуть на вход.

## 2. Раздел «Сотрудники» только у администратора

`GET /admin/users?page=1&limit=20`:

```text
{data:[Employee],pagination:{page,limit,total}}
Employee = {
  id: number, phone: string, full_name: string, department: string,
  position: string, role: "employee", is_active: boolean,
  must_change_password: boolean, created_at: UTC ISO string
}
```

Список содержит активных и заблокированных сотрудников, без администраторов.
Порядок: created_at DESC, id DESC. limit максимум 50. Показывать ФИО, телефон,
отдел, должность, активность и ожидание смены пароля; пагинацию, загрузку,
пустой результат, ошибку и ручной повтор чтения. При выходе очищать данные и
игнорировать запоздалые ответы предыдущей сессии, как в существующих экранах.

## 3. Создание сотрудника и однократный пароль

`POST /admin/users` принимает **только**:

```json
{"phone":"+77001234568","full_name":"Сотрудник","department":"Склад","position":"Кладовщик"}
```

Все поля обязательны. ФИО, отдел и должность обрезаются по краям: 1–120
Unicode-символов. Телефон использует существующую нормализацию Казахстана.
Не передавать role, password, is_active или must_change_password.

Ответ 201: `{data:{user:Employee,temporary_password:string}}`. Роль всегда
employee, is_active и must_change_password изначально true. Пароль генерирует
сервер. Показать отдельный экран/диалог результата с телефоном, временным
паролем и предупреждением о передаче лично сотруднику. Копирование — только
по явной кнопке; никакой автоматической записи в буфер обмена.

Пароль держать только в памяти открытого результата. После закрытия, выхода
или смены экрана очищать его. Не сохранять в localStorage/sessionStorage,
URL, логах, аналитике или DOM скрытого диалога. GET списка никогда не вернёт
его повторно. Во время POST блокировать повторное нажатие. После успеха
обновить список. `409 PHONE_EXISTS` — телефон уже занят, включая заблокированные
аккаунты. При сетевой неопределённости не повторять POST автоматически: обновить
список и объяснить, что ответ с паролем мог быть потерян. Восстановление/сброс
пароля и идемпотентный ключ на этом этапе отсутствуют; не обещать их пользователю.

## 4. Блокировка и активация

`PATCH /admin/users/:id`:

```json
{"is_active":false}
```

true активирует, false блокирует. Ответ 200: `{data:{user:Employee}}`.
Блокировка отзывает все сессии; активация требует нового входа и не снимает
обязательную смену пароля. Кнопку блокировать до ответа; после ответа обновить
строку по данным сервера. Повтор того же значения безопасен (200). При
неопределённом ответе сначала перечитать список, не переключать локально вслепую.
Администраторов этим API менять нельзя: 404. Удаления и смены ролей нет.

## 5. Ошибки и приёмка

Ошибки: `{error:{code,message,details?}}`. 400 — поля/JSON; 401 UNAUTHORIZED —
вход; 403 ACCOUNT_DISABLED — очистить состояние и вход с сообщением; 403
FORBIDDEN — доступ запрещён; 403 INVALID_ORIGIN — ошибка конфигурации origin;
404 — сотрудник не найден; 409 PHONE_EXISTS — дубликат; 409 PASSWORD_CHANGED —
повторный вход; 415 — нужен JSON; 429 — показать ожидание по Retry-After;
503 — временная занятость. Не выводить сырой серверный message/HTML.

Проверить обе локали RU/KZ и сценарий: admin → создать → показать пароль один
раз → выйти → employee → сменить пароль → создать обращение → admin → блокировка
→ старая сессия employee не работает → активация → новый вход работает.
Проверить reload/direct-link при обязательной смене, права employee на admin
маршруты, неверный пароль, дубликат телефона, двойной submit, потерю ответа,
истёкшую сессию и очистку секретов после выхода. Bootstrap проверяется отдельно
через CLI, браузерного экрана первичной настройки не добавлять.
