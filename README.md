# Голос команды

**Корпоративная система обратной связи и предложений сотрудников**

MVP, разработанный для хакатона ГК «Модус Трейд».

«Голос команды» — веб-приложение, через которое сотрудники могут сообщать о проблемах, предлагать улучшения, оставлять жалобы и благодарности, а руководители — рассматривать обращения и предоставлять обратную связь.

Главная идея: **каждое обращение должно попадать к ответственному сотруднику, иметь понятный статус и завершаться результатом, который видит автор.**

Проект представляет собой работающий прототип с интерфейсом на русском и казахском языках, серверной частью, базой данных и разграничением доступа.

## 1. Возможности

### Сотрудник

- Авторизация по номеру телефона и паролю.
- Создание обращений четырёх типов: проблема, предложение, жалоба, благодарность.
- Выбор направления обращения.
- Прикрепление изображений и PDF.
- Просмотр собственных обращений, их статусов и истории.
- Получение решения и комментария ответственного.

### Руководитель

- Просмотр обращений, назначенных лично ему.
- Доступ к описанию, вложениям и истории обращения.
- Перевод обращения на рассмотрение.
- Завершение или отклонение обращения с обязательным комментарием.
- Ограничение доступа только назначенными обращениями.

### Администратор

- Просмотр общей очереди и базовой статистики.
- Создание и блокировка учётных записей сотрудников и руководителей.
- Сброс паролей.
- Создание направлений с названиями RU/KZ.
- Назначение ответственных руководителей по направлениям.
- Архивирование и восстановление направлений.
- Ручное переназначение обращений.
- Поиск незавершённых обращений без действующего ответственного.
- Просмотр авторов и истории обращений.

## 2. Роли и права доступа

| Возможность | Сотрудник | Руководитель | Администратор |
|---|:---:|:---:|:---:|
| Создание обращений | Да | Нет | Нет |
| Просмотр своих обращений | Да | — | Да* |
| Просмотр назначенных обращений | Нет | Да | Да |
| Изменение статусов | Нет | Да | Да |
| Управление пользователями | Нет | Нет | Да |
| Управление направлениями | Нет | Нет | Да |
| Просмотр статистики | Нет | Нет | Да |

\* Администратору доступны все обращения системы.

Проверка прав выполняется на сервере, а не только посредством скрытия элементов интерфейса.

## 3. Быстрый запуск на Windows

### Требования

- Windows 10/11 с PowerShell.
- Node.js **24.13.0 или новее**.
- npm.
- Git — для клонирования репозитория.

Дополнительные облачные сервисы для локального запуска не требуются.

### Шаг 1. Получить исходный код

```powershell
git clone https://github.com/egorkitsun2/Hackathon-2026.git
cd Hackathon-2026
```

### Шаг 2. Установить зависимости

```powershell
npm.cmd --prefix backend ci
```

### Шаг 3. Создать тестовые аккаунты

**Только при первом запуске на чистой базе данных:**

```powershell
npm.cmd --prefix backend run seed
```

Команда создаёт два аккаунта сотрудников и один аккаунт администратора.

Логины и случайно сгенерированные пароли сохраняются локально:

`backend/.local/test-accounts.json`

Откройте этот файл и используйте нужные учётные данные. Файл исключён из Git и не должен публиковаться.

**Важно:** повторно выполнять `seed` на уже используемой базе не нужно. Команда откажется перезаписывать существующие аккаунты.

### Шаг 4. Запустить приложение

Из корня репозитория:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start-local.ps1
```

После успешного запуска откройте:

**http://localhost:8787**

Проверка доступности API:

http://localhost:8787/api/v1/health

При исправной работе возвращается:

```json
{
  "data": {
    "status": "ok",
    "database": "ok"
  }
}
```

Сайт и API работают через один адрес. Отдельно запускать frontend через Live Server не требуется.

Для остановки используйте `Ctrl+C` в терминале запуска либо:

```powershell
.\stop-demo.ps1
```

### Если база уже существует

Не запускайте `seed` повторно и не удаляйте базу.

Используйте ранее созданные аккаунты. Если нужен первый администратор для новой базы без тестовых пользователей:

```powershell
npm.cmd --prefix backend run bootstrap:admin
```

Учётные данные администратора будут сохранены в `backend/.local/bootstrap-admin.json`.

Более подробная инструкция: [Локальная настройка Windows](docs/windows-local-setup.md).

## 4. Демонстрационный сценарий для жюри

Рекомендуемый сценарий показывает полный жизненный цикл обращения.

**Шаг 1. Администратор**

Войти под тестовым администратором. Открыть «Пользователи» и создать руководителя. Система выдаст временный пароль, который отображается однократно.

**Шаг 2. Настройка маршрутизации**

Открыть «Маршрутизация», создать направление, например «Техническая поддержка», и назначить ответственного руководителя.

По умолчанию предусмотрены направления IT, Закупки и Администрация. Можно создавать собственные.

**Шаг 3. Сотрудник**

Войти под тестовым сотрудником, нажать «Создать обращение», выбрать направление и заполнить форму.

Пример:

- Тип: Проблема
- Направление: IT
- Тема: Не работает сканер штрихкодов
- Описание: Сканер на складе не считывает коды товаров, что задерживает обработку заказов.

При необходимости прикрепить изображение.

**Шаг 4. Руководитель**

Войти под созданным руководителем, предварительно сменив временный пароль.

Открыть назначенное обращение, взять его на рассмотрение, затем завершить с комментарием о выполненных действиях.

**Шаг 5. Результат для сотрудника**

Снова войти под сотрудником и открыть своё обращение.

Проверить, что изменился статус, появился комментарий руководителя и сохранилась история обработки.

**Шаг 6. Проверка административного контроля**

Администратор может заблокировать руководителя. Его незавершённые обращения будут отмечаться как требующие переназначения.

Переназначение выполняется вручную; история обращения сохраняется.

**Дополнительный сценарий:** архивировать направление, проверить, что оно исчезло из формы новых обращений, но ранее созданные обращения остались доступны.

## 5. Техническая архитектура

| Компонент | Технология |
|---|---|
| Frontend | HTML, CSS, JavaScript |
| Backend | Node.js, TypeScript, Hono |
| База данных | SQLite (`node:sqlite`) |
| Пароли | Argon2id |
| Авторизация | Серверные сессии, HttpOnly cookies |
| API | REST, JSON |
| Файлы | Локальное защищённое хранилище |
| Локальный запуск | PowerShell, Node.js |
| Публичная демонстрация | Cloudflare Quick Tunnel |

### Принцип работы

```text
Браузер сотрудника
        |
        v
Frontend (HTML / CSS / JS)
        |
        | HTTP / REST API
        v
Backend (Node.js + Hono)
        |
        +---- SQLite
        |     Пользователи
        |     Обращения
        |     Направления
        |     Назначения
        |     История событий
        |
        +---- Хранилище вложений
```

Frontend и API обслуживаются одним сервером и одним origin.

### Структура репозитория

```text
Hackathon-2026/
├── backend/
│   ├── src/            # Сервер и бизнес-логика
│   ├── migrations/     # Миграции SQLite
│   ├── scripts/        # Служебные команды
│   └── tests/          # Тесты backend
├── frontend/
│   ├── index.html      # Точка входа
│   ├── css/            # Стили
│   ├── js/             # Логика интерфейса
│   ├── tests/          # Тесты frontend
│   └── qa/             # Браузерные проверки
├── docs/               # API и инструкции
├── start-local.ps1     # Локальный запуск
├── start-demo.ps1      # Публичный демозапуск
└── stop-demo.ps1       # Остановка
```

Полное описание API: [docs/api-contract.md](docs/api-contract.md).

## 6. Логика маршрутизации

Каждое направление имеет уникальный неизменяемый код, названия на русском и казахском языках и необязательного ответственного руководителя.

При создании обращения система определяет руководителя по выбранному направлению.

Если действующий руководитель не назначен, обращение остаётся доступным администратору для ручной обработки или назначения.

При блокировке руководителя существующие назначения не удаляются автоматически. Незавершённые обращения с заблокированным ответственным можно найти через специальный административный фильтр.

Архивирование направления запрещает создание новых обращений в нём, но сохраняет существующие обращения, вложения и историю. Направление по умолчанию «Администрация» архивировать нельзя.

## 7. Статусы обращений

```text
Новое
  |
  v
На рассмотрении
  |
  +----> Решено
  |
  +----> Отклонено
```

При завершении или отклонении требуется комментарий.

Система фиксирует историю изменения статусов. Повторное открытие закрытых обращений в текущем MVP не предусмотрено.

## 8. Загрузка вложений

Поддерживаются:

- JPEG / JPG
- PNG
- WebP
- PDF

Ограничения: до трёх файлов на обращение, каждый размером не более 5 МиБ.

Вложения хранятся отдельно от публичных файлов frontend. Доступ к скачиванию проверяется через серверную авторизацию и права на конкретное обращение.

## 9. Безопасность

В прототипе реализованы:

- Хеширование паролей с Argon2id.
- HttpOnly cookies и серверное хранение сессий.
- Secure cookies в HTTPS-режиме.
- Проверка ролей и прав доступа на backend.
- Проверка Origin для запросов, изменяющих состояние.
- Ограничение попыток входа.
- Проверка входных данных на сервере.
- Параметризованные SQL-запросы.
- Ограничение типов и размеров вложений.
- Отзыв сессий при блокировке пользователя.
- Исключение файлов БД, паролей и локальных данных из Git.

В текущем MVP отсутствуют полноценное антивирусное сканирование вложений и промышленная инфраструктура мониторинга.

## 10. Запуск автоматических тестов

Из корня проекта после установки зависимостей:

**Backend:**

```powershell
npm.cmd --prefix backend run typecheck
npm.cmd --prefix backend test
npm.cmd --prefix backend run build
```

**Frontend:**

```powershell
node --test frontend/tests/*.test.mjs
```

Тесты backend проверяют в том числе авторизацию, права доступа, маршрутизацию, обработку обращений, вложения и миграции БД.

Основные тесты используют изолированные базы данных и не требуют очистки демонстрационной базы.

Также предусмотрены отдельные браузерные QA-сценарии в `frontend/qa/`. Для них необходима дополнительная тестовая среда, описанная в документации frontend.

## 11. Публичная демонстрация

Для временного публичного доступа можно использовать Cloudflare Quick Tunnel.

Требуется `cloudflared.exe` в PATH.

После остановки локального сервера выполните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start-demo.ps1
```

Скрипт выведет адрес вида:

`https://<случайное-имя>.trycloudflare.com`

Открывайте именно адрес, который выведен в терминале.

**Важно:**
- Адрес меняется при новом запуске.
- Терминал запуска должен оставаться открытым.
- Наличие интернета и доступность Cloudflare обязательны.
- Учётные данные передаются проверяющим отдельно.
- Это временный демонстрационный туннель, не постоянный хостинг.

Остановка:

```powershell
.\stop-demo.ps1
```

Подробнее: [docs/windows-launchers.md](docs/windows-launchers.md).

## 12. Ограничения MVP

Проект разработан в рамках хакатона и не позиционируется как готовая к промышленному внедрению корпоративная платформа.

В текущую версию не входят:

- Анонимная подача обращений.
- Публичная регистрация и самостоятельное восстановление доступа.
- Email/SMS/push-уведомления.
- Интеграции с 1С, Bitrix24 и другими корпоративными системами.
- Автоматическое переназначение обращений.
- Настраиваемые SLA и сроки обработки.
- Удаление пользователей и обращений.
- Переименование уже созданных направлений.
- Повторное открытие завершённых обращений.
- Расширенная аналитика и отчётность.

Для реального корпоративного внедрения потребуются дополнительное нагрузочное и защитное тестирование, мониторинг, резервное копирование, политика обработки персональных данных и промышленная схема развёртывания.
